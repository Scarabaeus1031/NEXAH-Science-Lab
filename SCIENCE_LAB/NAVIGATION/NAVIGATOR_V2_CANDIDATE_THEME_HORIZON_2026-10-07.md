# NEXAH Navigator v2 — Candidate Theme Horizon

**Date:** `2026-10-07`

**Status:** `ASSESSMENT_BACKLOG / NAVIGATOR_V1_FROZEN / NO_PROMOTION / NO_NEW_CLAIM / INTERNAL_ONLY`

## 1. Purpose

This record answers a bounded question:

> Which large NEXAH themes are materially present across the repositories but
> are not yet adequately visible in Navigator v1, and how could they connect
> to the existing architecture without flattening their evidence status?

It is a planning and archaeology record. It does not change the frozen
Navigator, add a module, create a route, alter the six entry domains, extend
the seven canonical Connection Families or promote an archive object.

The current architecture is the constraint that makes this assessment useful:

- six entry domains: Orientation, Framework, Families, Language, Atlas and
  Evidence;
- seven canonical Connection Families (`CF:F1–F7`);
- fifteen conceptual modules and their governed representations;
- explicit evidence, provenance, non-identity and claim-ceiling rules;
- public scope remains zero.

## 2. Main finding

The largest gap is not another isolated visual family. It is the missing
**scale and nesting coordinate** that can explain how one declared record,
carrier or frame sits inside another without turning resemblance into identity.

The repository already contains four different things that have often been
seen together but must remain distinguishable:

1. **Matryoshka as a conceptual lens** — nested carriers, frames and scales;
2. **exact scale coordinates** — for example the dyadic scale elevator
   `u = log₂(r)` and the action `Eₖ(u) = u + k`;
3. **empirical cross-scale tests** — including IEEE scaling-pattern work;
4. **negative controls** — including CAL01, where a multi-scale invariant was
   not found.

Navigator v1 can show families and relations, but it does not yet let a reader
ask, with sufficient precision:

> At which scale is this record valid, what contains it, what changes during a
> scale transition, and what survives the return?

That is the strongest candidate for a later v2 addition.

## 3. Matryoshka / Nested Scale assessment

### 3.1 Source meaning

The current Mission Control definition is bounded: Matryoshka names nested
carriers, frames or scales. An apparent outside may be the inside of a wider
declared record. It does not establish an absolute outside, infinite physical
nesting or a universal fractal mechanism.

This aligns with the existing NEXAH method because every record already has a
source, selection, frame, scale, medium and time. A downstream record can in
turn become the source of another operation.

### 3.2 Proposed architectural role

Matryoshka should not become an eighth Connection Family. It is better treated
as a **cross-family framework lens** over the current graph.

| Scale-lens field | Question |
|---|---|
| `carrier_at_scale` | What is the declared object or record at this level? |
| `contains / contained_by` | Which carrier or frame contains which other record? |
| `scale_coordinate` | Is the scale ordinal, metric, logarithmic, temporal or domain-specific? |
| `scale_transition` | Which declared operator moves between levels? |
| `preserved / lost / added / unresolved` | What changes under that move? |
| `return_record` | Can the lower- or higher-scale view be compared with its source? |
| `evidence_scope` | Is the relation conceptual, exact, simulated, empirical or only visual? |

Primary family connections:

- `CF:F1 Observation / Record` — each level must remain a separately typed
  record;
- `CF:F2 Address / Boundary` — containment and resolution require explicit
  boundaries and addresses;
- `CF:F3 Transition / Operator` — changing scale is an operation, not a visual
  implication;
- `CF:F5 Connectivity / Topology` — nesting may alter visible adjacency without
  changing source identity;
- `CF:F7 Validation / Governance` — evidence and claim ceilings do not transfer
  automatically between scales;
- `CF:F4 Phase / Drift` enters only where scale is itself dynamical or coupled
  to time/phase by a declared map.

### 3.3 Scale distinctions that must remain visible

| Scale use | Repository example | What may be said | What may not be said |
|---|---|---|---|
| Conceptual nesting | Mission Control Matryoshka / TOP lens | records and frames can be nested | all nested forms share one mechanism |
| Exact coordinate | Multi-Grid scale elevator | `Z₆ × Z` can keep fold phase and dyadic scale separate | radial appearance proves phase-scale coupling |
| Empirical campaign parameter | IEEE load-scale campaigns | ordered benchmark states can be compared across declared load scale | load scale is time or a universal physical scale |
| Cross-system size comparison | IEEE Scaling Pattern v2 | tested cases and negative precursor result can be shown | a predictive scaling law was found |
| Negative control | CAL01 | tested multi-scale invariant was not found | calendar recurrence proves a scale invariant |
| Representation level | Pascal threads, grids, GLB and projections | one relation can have multiple views and resolutions | equal count or similar geometry means equal structure |

### 3.4 Required gate before implementation

A v2 scale lens should not be built until a small machine-readable fixture
contains at least:

1. three nested records with stable identities;
2. two declared scale transitions;
3. one exact transition and one empirical or simulated transition;
4. ILAU plus residual and return for every edge;
5. one negative control;
6. an explicit statement that nesting is not mechanism identity.

### 4.1 Formal Scientific Reasoning Bridge — gap and asset crosswalk

The Jonathan Gorard / Lanyon comparison identifies a real neighbour, but it
also corrects an overly simple gap list. NEXAH does not start from zero. OLS,
ORION, the Science Lab and the Navigator each own part of the required chain;
the missing object is an adopted, tested end-to-end bridge.

| Required capability | What NEXAH already has | Current gap | Candidate bridge action |
|---|---|---|---|
| Formal grammar | OLS 1.0 is an implementation-independent semantic language with stable identifiers, declarations, type rules, composition semantics and conformance rules | no single normative carrier syntax, parser, evaluator or runtime | define one bounded machine profile without silently extending OLS |
| Operator signatures | OLS operator contracts; multiple typed local ledgers; ORION immutable Operator Registry | signatures are not normalized across domains and the ORION registry is non-executing | freeze domain, codomain, units, assumptions, version, failure and evidence fields for one model |
| Units and dimensions | local scientific packages and lab reports declare units where required | no ecosystem-wide dimensional type checker or quantity calculus | add dimensional contracts only to the one-model fixture; compare with established unit/type systems before inventing a standard |
| Executable transformations | many package-local scripts; ORION historical Transformation Engine performs deterministic route planning; Runtime 1.1 is an unadopted executable candidate | no adopted general operator executor; planning is not execution | implement one owned adapter with explicit version and stop conditions; do not certify general ORION capability from it |
| Formal claim dependencies | typed Navigator relations, claim ceilings, Science Lab promotion rules and Representation/Evidence Ledgers | documentary links do not yet form an executable assumption→claim→failure graph | encode one claim graph with destruction controls and dependency invalidation |
| Experiment adapters | reproducible Science Lab packages, Labreport schema, manifests, hashes and machine results | no common observation/simulation adapter consumed by Navigator and ORION | ingest one frozen simulation record and one deliberately incompatible control through a versioned interface |
| Machine-checkable return | exact local return tests and ORION O8 full-endpoint transformation/inverse recovery within its registered scope | no general source→prediction→observation→reconstruction return contract | define equality/tolerance, preserved/lost fields and set-valued ambiguity for the fixture |
| Abstention and open residuals | fail-closed Navigator admission; ILAU; ORION `UndefinedBoundary`, `AmbiguityCause` and `InformationLossBoundary`; explicit negative/open results | statuses are distributed and not propagated end-to-end | normalize `unknown`, `undefined`, `not_identifiable`, `not_testable`, `abstain` and residual ownership without collapsing them |

The intended long-horizon chain is:

```text
Navigator question and source context
→ OLS semantic contract
→ typed operator / quantity specification
→ ORION-scoped deterministic planning or execution adapter
→ implementation / proof / simulation / observation records
→ Representation + Evidence Ledger
→ Navigator return with claim ceiling and Human authority
```

This chain is a candidate architecture, not a statement of present
interoperability. Current authoritative boundaries remain:

- OLS supplies formal semantics but no mandatory runtime;
- ORION V1 is a certified deterministic structural orientation core, not a
  general scientific reasoner;
- the historical Transformation Engine plans routes but does not execute
  scientific operators;
- the ORION→NEXAH operational adapter remains `UNDEFINED`;
- the Navigator explains OLS and ORION but does not extend or certify either;
- mathematical/implementation correctness does not establish semantic,
  theoretical or empirical correctness.

## 6. Recommended minimal v2 scope

If the Human Owner later reopens the freeze, the smallest coherent v2 should
add only three architectural capabilities:

### 6.1 Scale / Matryoshka lens

A reader can move between nested records and see the declared scale,
containment, transition, ILAU, residual, evidence grade and return.

### 6.2 Method spine

A reader can follow one common chain:

```text
Source → Record → Frame/Cut → Projection → Comparison → Reconstruction → Return
```

The chain should point into Sealed Comparison, Pattern Toolbox, NEXAH Compare
and Readout Reconstruction without claiming that they are one implementation.
Its consequential edges should expose a bounded Representation Ledger view:
source/operator/target boundary, scope, preservation, loss, collision,
uncertainty, invertibility, evidence, provenance and claim support. The current
Ledger is a structured-provenance candidate; its blocked validator path must
not be revived by interface language.

### 6.3 Ecosystem edge ledger

A reader can see how Mission Control, Core, ORION, Science Lab, Navigator and
NEXAHEDRON exchange records and authority. Each edge must state what is
preserved, lost, added and unresolved and where Human Return occurs.

The six entry domains and seven Connection Families can remain unchanged.
Applications, operators, 3D constellations and Human Return can then be added
as governed projections onto this stronger substrate rather than as competing
top-level architectures.

## 7. Candidate admission gates

No candidate enters a later Navigator build merely because files exist. A
candidate must provide:

1. a stable identity and owner;
2. a plain-language question;
3. controlling source paths;
4. a declared object, frame, scale and operator;
5. relation to an existing domain, module and Connection Family;
6. evidence grade and current result;
7. claim ceiling and explicit nonclaims;
8. ILAU/residual/return where a transformation is asserted;
9. a distinction between source, representation and evidence;
10. a reason it cannot be explained adequately through an existing module;
11. deterministic validation where a machine-readable surface is proposed;
12. an explicit Human Owner reopen/version decision.

## 8. Do not promote yet

The following shortcuts would weaken the architecture:

- no `CF:F8` for scale, Matryoshka, experience or 3D;
- no universal scale law inferred from repeated nested visuals;
- no Field Navigation product claim from its exploratory archive;
- no autonomous semantic discovery claim for NEXAH Compare;
- no scientific-evidence status for HTML or GLB appearance alone;
- no fusion of Human Return, system control and scientific validation;
- no new top-level domain merely to accommodate a large folder;
- no public allowlisting during this assessment.
