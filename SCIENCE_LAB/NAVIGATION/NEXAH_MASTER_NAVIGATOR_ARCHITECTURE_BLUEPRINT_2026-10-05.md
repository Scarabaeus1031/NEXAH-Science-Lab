## 1. Decision

The next build should be a repository-native static navigator:

```text
NEXAH_LAB_NAVIGATOR.html
```

It is not yet `nexah.de`, not a replacement for Mission Control, not a new
scientific authority and not an integrated NEXAH machine. It is the Human
entry and catalog surface for the current NEXAH Science Lab repository.

Its purpose is to answer:

1. Where should I begin?
2. Which module is current for this function?
3. Which pages are variants, supporting views or historical sources?
4. Which family connections are registered?
5. Where is the owning record and its claim boundary?
6. Which HTML, 3D asset and document belong to the same module family?

Mission Control remains the authority for current operational truth, Human
Owner routing and activation gates. The Lab Register remains the maintained
study-status record. Owning case-study packages remain the scientific evidence
authority.

## 3. Why the overview became difficult

Four different organizational layers currently overlap:

1. physical HTML files and their copies;
2. functional module families;
3. scientific or methodological connection families;
4. historical 3D constellations.

One module may have several HTML views, images, records and 3D expressions.
Conversely, one HTML may contain several views or submodules. Counting files
therefore creates both inflation and omission.

### Critical taxonomy collision

The September HTML-Lab router and the October Family Connection Map both use
labels such as `F1`, `F2`, and `F7`, but they do not mean the same thing.

The Family Connection Map v2 currently means:

```text
CF:F1  Observation / Record
CF:F2  Address / Boundary
CF:F3  Transition / Operator
CF:F4  Phase / Drift
CF:F5  Connectivity / Topology
CF:F6  Synchronization / Control
CF:F7  Validation / Governance
```

The older HTML-Lab router used a different eight-part ordering:

```text
HL:F1  Observation / Selection / Cut / Record / Return
HL:F2  Projection / Shadow / Mask / Visibility
HL:F3  Carrier / Address / Grid / CRT
HL:F4  Frame / Tessarec / Root Space / Green Bridge
HL:F5  Time / Phase / Rhythm / Five-H
HL:F6  Number / Prime / Euler / Fibonacci / Mirror
HL:F7  Runtime / Receipts / Comparison Infrastructure
HL:F8  Human Instruments / Games / Cultural Orientation
```

These labels must never be merged without a namespace. The Master Navigator
must display names first and codes second.

Required namespaces:

- `CF:F1..F7` — Connection Families v2;
- `HL:F1..F8` — historical HTML-Lab functional shelves;
- `3D:C-01..C-12` — frozen 3D constellations;
- `SUBJ:*` — subject entrances;
- `MOD:*` — stable module-family identifiers;
- `ART:*` — physical artifact identifiers when needed.

## 5. What should be built

### Phase-1 product

`NEXAH_LAB_NAVIGATOR.html` should be a single static, offline-capable entry
surface generated from curated registries. It should live in `SCIENCE_LAB/`.

It is repository-native because its owning links, records and artifacts are in
this repository. It may later be projected into NEXAH Experience or
`nexah.de`, but that public projection is a separate publication decision.

It should not be named Mission Control. Mission Control is an operational and
governance role, while the Navigator is a read-only Human entrance.

### Required views

1. **Start by intention**
   - understand a concept;
   - open an instrument;
   - inspect evidence;
   - browse a module family;
   - enter the historical/3D archive.

2. **Current modules**
   - Ring 1 modules;
   - current master surface;
   - related surfaces;
   - family chain;
   - evidence and claim ceiling.

3. **Connection atlas**
   - direct deep links into the Family Connection Map;
   - named relations rather than unqualified `F` codes.

4. **HTML catalog**
   - master, supporting, variant, historical, source-only and duplicate;
   - filters by Human, Builder and Science role;
   - technology indicators for canvas, SVG, iframe and WebGL;
   - no implication that every file is an independent project.

5. **3D constellations**
   - twelve constellation entrances;
   - current evidence level;
   - HTML viewer ↔ 3D asset pairing where verified;
   - no gallery of all 1,850 legacy files.

6. **Status and authority**
   - Mission Control currentness link;
   - Lab Register study status;
   - owning evidence record;
   - explicit distinction between navigation, execution and activation.

### What it should not do

- no iframe wall containing every instrument;
- no automatic execution chain;
- no silent master selection based on filename or visual quality;
- no copying scientific results into a second authority surface;
- no publication of private Mission Control state;
- no forced merging of MIWA, LOKI, Tessarec, Root7 or 3D scenes;
- no move, rename or deletion of source/custody artifacts;
- no assumption that a 3D object is an executable or validated module.

## 6. Registry architecture

The current Ring-1 registry is a useful prototype but is too small for the
whole corpus. Registry v2 should separate five entities.

### Module

One stable conceptual or executable family.

Required fields:

```text
module_id
title
summary
human_role
builder_role
science_role
current_master_surface
status
evidence_class
claim_ceiling
owning_record
connection_routes[]
subject_routes[]
related_modules[]
```

### Surface

One HTML entry or view belonging to a module.

```text
surface_id
module_id
path
role = master | supporting | variant | historical | source-only | duplicate
runtime = static | canvas | svg | iframe | webgl | three-js
offline_status
predecessor
successor
```

### Relation

A typed connection between modules or families.

```text
relation_id
source
target
type = exact | empirical | method | open | non-identity
explanation
evidence_record
claim_boundary
```

### Media asset

A 3D model, image, data file or downloadable package.

```text
asset_id
module_id
path_or_custody_locator
media_type
sha256
viewer_surface
provenance_status
semantic_status
```

### Record

The owning scientific, implementation or governance document.

The navigator links to the record. It does not copy the record's result or
change its status.

## 8. 3D integration rule

The Master Navigator should expose module-level 3D entrances, not raw asset
volume.

A 3D item enters current navigation only when all of the following exist:

1. a stable module-family assignment;
2. a custody locator or repository path;
3. a declared viewer or rendering route;
4. an evidence level from A to D;
5. a statement of what the geometry demonstrates;
6. a statement of what it does not demonstrate.

The existing twelve 3D constellations remain the top-level archive map:

## 11. Acceptance criteria for the Master Navigator

The first master build is ready only if a reader can answer, without opening
the filesystem manually:

- What is the current entry for this function?
- Is this page a master, supporting view, variant, historical source or copy?
- Which module family owns it?
- Which Connection Map relation applies?
- Which subject entrance applies?
- Is there an associated 3D expression?
- What is the evidence class?
- What is the claim ceiling?
- Where is the owning record?
- What is current, and what is frozen archive?

Technical gates:

- zero missing paths in the curated registry;
- zero duplicate module IDs;
- every active module has an owning record and claim ceiling;
- every promoted surface has an explicit predecessor/variant decision;
- direct `file://` operation;
- keyboard-accessible navigation;
- no runtime errors in the current-master smoke set;
- archives and custody files remain byte-unchanged.
